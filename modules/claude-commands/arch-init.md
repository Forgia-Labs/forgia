Initialize the project's DDD architecture from a human-provided brief.

## Instructions

Given arguments: $ARGUMENTS

1. **Parse arguments**:
   - Extract the human brief (everything except flags)
   - Detect `--enrich` flag: if present, enable codebase-memory-mcp enrichment
   - If no brief is provided and no `--enrich` flag, treat as empty project (generate templates with TODOs)

2. **Pre-flight checks**:

   a. Verify `.forgia/` exists. If not, tell the user: "Vault non inizializzato. Esegui `/project-init` prima."

   b. Check if `.forgia/architecture/` directory already exists AND contains any `.yaml` files. If it does, **refuse** and tell the user:
      "Architettura gia' presente in `.forgia/architecture/`. Usa `/arch-update` per modificarla."
      — then stop. Do NOT overwrite existing architecture files.

3. **Read project context** — scan for these files and read any that exist:
   - `.forgia/constitution.md`
   - `README.md`
   - `ARCHITECTURE.md`, `docs/ARCHITECTURE.md`
   - `docs/*.md`
   - `go.mod` (detect Go stack)
   - `package.json` (detect Node/React stack)
   - `Cargo.toml` (detect Rust stack)
   - `pyproject.toml`, `requirements.txt` (detect Python stack)
   - `pom.xml`, `build.gradle` (detect Java stack)
   - `.forgia/config.toml`
   - Actually **read the content** of discovered files — do not just list them.

4. **Read vault template schemas** — these define the exact YAML structure for output:
   - `modules/vault-template/architecture/system-context.yaml`
   - `modules/vault-template/architecture/containers.yaml`
   - `modules/vault-template/architecture/technology-decisions.yaml`
   - `modules/vault-template/architecture/quality-attributes.yaml`
   - `modules/vault-template/architecture/constraints.yaml`
   - `modules/vault-template/architecture/glossary.yaml`
   - `modules/vault-template/contexts/_template.yaml`

5. **Optional enrichment** — only if `--enrich` flag was provided:

   a. Check if codebase-memory-mcp is available by attempting to call `list_projects`.
   b. If available, call these MCP tools to enrich the architecture:
      - `list_projects` — discover existing project structure
      - `get_architecture` — retrieve existing architecture knowledge
      - `search_graph` with relevant terms from the brief — find relationships, routes, packages, call paths
   c. If codebase-memory-mcp is NOT available, warn the user:
      "codebase-memory-mcp non disponibile. Procedo senza enrichment dal codice."
      — then continue without enrichment. Do NOT fail.
   d. Merge enrichment data with the brief: enrichment fills gaps, brief takes precedence for explicit choices.

6. **Analyze the brief** and determine:
   - **System name**: inferred from README, project directory, or brief
   - **Actors**: who/what interacts with the system (users, external systems, APIs)
   - **Containers**: services, databases, frontends, message queues mentioned in the brief
   - **Technology decisions**: languages, databases, protocols, frameworks mentioned
   - **Bounded contexts**: distinct domain areas implied by the brief
   - **Glossary terms**: domain-specific terms from the brief

   If the brief is empty or not provided, generate placeholder structures with TODO markers for every field.

7. **Generate architecture files** — create these files in `.forgia/architecture/`:

   ### `.forgia/architecture/system-context.yaml`
   ```yaml
   # C4 Level 1: System Context
   # Generated by /arch-init from brief. Review and refine.

   name: "<system-name>"
   description: "<one-sentence description from brief>"

   actors:
     - name: "<actor-name>"
       type: "<person | system>"
       description: "<who/what this actor is>"
       interactions:
         - target: "<container or system part>"
           protocol: "<http | grpc | event | cli | file>"
           description: "<what the interaction does>"
   ```
   - Generate one actor entry per detected actor from the brief
   - If no actors detected, create one placeholder with TODO comments

   ### `.forgia/architecture/containers.yaml`
   ```yaml
   # C4 Level 2: Container Diagram
   # Generated by /arch-init from brief. Review and refine.

   containers:
     - name: "<container-name>"
       technology: "<e.g. Go, Python, PostgreSQL>"
       description: "<what this container does>"
       bounded_context: "<context-name>"
       ports: []
       depends_on: []
   ```
   - Generate one container entry per detected service/process/database
   - Link each container to its bounded context
   - If no containers detected, create one placeholder with TODO comments

   ### `.forgia/architecture/technology-decisions.yaml`
   ```yaml
   # Technology Decisions (ADR-style)
   # Generated by /arch-init from brief. Review and refine.

   decisions:
     - id: "TD-001"
       title: "<short description>"
       status: "proposed"
       date: "<today's date YYYY-MM-DD>"
       context: "<why this technology was chosen>"
       decision: "<what was decided>"
       alternatives: []
       consequences: []
   ```
   - Generate one decision per technology choice mentioned in the brief (language, database, protocol, framework)
   - Number sequentially: TD-001, TD-002, etc.
   - If no technology decisions detected, create one placeholder with TODO comments

   ### `.forgia/architecture/quality-attributes.yaml`
   ```yaml
   # Quality Attributes
   # Generated by /arch-init from brief. Review and refine.

   attributes:
     - name: "<!-- TODO: define quality attribute -->"
       description: "<!-- TODO: describe what this means for the system -->"
       target: "<!-- TODO: measurable goal -->"
       priority: "medium"
       rationale: "<!-- TODO: why this target -->"
   ```
   - Always generate with TODO placeholders — quality attributes require human input
   - If the brief mentions specific NFRs (latency, uptime, etc.), pre-fill those

   ### `.forgia/architecture/constraints.yaml`
   ```yaml
   # Constraints
   # Generated by /arch-init from brief. Review and refine.

   constraints:
     - name: "<!-- TODO: constraint name -->"
       type: "<!-- TODO: budget | team | timeline | compliance | technical -->"
       description: "<!-- TODO: what the constraint is -->"
       impact: "<!-- TODO: how this affects architecture decisions -->"
   ```
   - Always generate with TODO placeholders — constraints require human input
   - If the brief mentions specific constraints, pre-fill those

   ### `.forgia/architecture/glossary.yaml`
   ```yaml
   # Glossary — Ubiquitous Language
   # Generated by /arch-init from brief. Review and refine.

   terms:
     - term: "<domain-term>"
       meaning: "<definition in project context>"
   ```
   - Extract domain-specific terms from the brief
   - If no terms detected, create one placeholder with TODO comments

8. **Generate bounded context files** — create one file per detected context in `.forgia/contexts/`:

   ### `.forgia/contexts/<context-name>.yaml`
   ```yaml
   # Bounded Context: <Context Name>
   # Generated by /arch-init from brief. Review and refine.

   name: "<context-name>"
   responsibilities:
     - "<what this context owns>"

   ubiquitous_language:
     - term: "<context-specific term>"
       meaning: "<definition>"

   interfaces:
     - with: "<other-context-name>"
       protocol: "<http | grpc | event | shared-db>"
       contract: "<!-- TODO: define contract -->"
       direction: "<inbound | outbound | bidirectional>"

   dependencies:
     depends_on: []
     depended_by: []

   status:
     reviewed: false
     fd_created: false
     fd_completed: false
   ```
   - Name files in kebab-case: `<context-name>.yaml`
   - Each context must have `reviewed: false`
   - If no bounded contexts can be detected from the brief, create one placeholder context named `core.yaml`

9. **YAML formatting rules** — apply to ALL generated files:
   - 2-space indentation (no tabs)
   - Quote strings that contain special characters (`:`, `#`, `{`, `}`, `[`, `]`, `,`, `&`, `*`, `?`, `|`, `-`, `<`, `>`, `=`, `!`, `%`, `@`, `\`)
   - No trailing whitespace
   - Empty arrays: `[]` on the same line
   - Comment header at the top of each file

10. **Report results** to the user:
    - List all created files
    - Show counts: "Creati N container e M bounded context."
    - Suggest next step: "Prossimo passo: rivedi i file generati e poi esegui `/arch-review` per la validazione."

## Important

- **Never overwrite** existing `.forgia/architecture/` or `.forgia/contexts/` files — if they exist, refuse and suggest `/arch-update`
- The brief is the primary input — generate best-effort architecture from it
- With `--enrich`, codebase-memory-mcp is supplementary — brief always takes precedence
- Without `--enrich`, do NOT attempt to use codebase-memory-mcp
- On empty project (no brief, no context files): generate all files with TODO placeholders throughout
- Generated YAML must conform exactly to the schemas in `modules/vault-template/`
- Do NOT read files matching guardrail deny patterns: `**/.env`, `**/*.pem`, `**/*.key`, `**/.ssh/id_*`, `**/.aws/credentials`
- Do NOT write to: `.forgia/constitution.md`, `.forgia/config.toml`, `.forgia/guardrails/deny.toml`
- All generated files should have a comment header noting they were generated by `/arch-init` and should be reviewed
